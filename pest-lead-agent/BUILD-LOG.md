# Build log

Dated 2026-10-11. An honest record of what actually went wrong or surprised me while building and testing this demo, and what I did about it. Entries are in the order they happened. Nothing here is invented to look dramatic; most of the build went to plan, and the list is short for that reason. The machine clock in the result files is UTC and shows 2026-10-10 late evening for the same session.

## Changes of plan during the build (not failures)

1. **No API key, so a bridge.** The first brief had the recorder and live mode call `api.anthropic.com` with a key from Doppler. Midway I was told there is no API key and no API billing, so the live path became a local bridge that answers Messages API requests with the logged-in `claude` CLI. The workflow node did not change, only its base URL.
2. **Bridge rules tightened twice.** First the bridge moved to a dedicated sign-in folder (never the default `~/.claude`), then a separate worker rewrote it as the shared, hardened `_shared/claude-bridge/`. My own first version of the bridge is gone. Because the rule arrived after I had already recorded, the first set of recordings was made with the default login (before the rule existed). I re-recorded all 11 under the dedicated folder once it was available, so every recording in the repo now comes from the dedicated sign-in.
3. **n8n 2.38.7 became 2.42.6.** The repo-level n8n rules pinned the user's global install. The suite had been written against 2.38.7 via `pnpm dlx`; switching to the global binary needed no workflow change and passed on the first run (apart from a typo in my own test, below).
4. **House-style rules arrived late** (workflow ids, names, notes, retries, idempotency keys, rules in a sheet, no personal data in Slack/ClickUp/Sheets, n8n-mcp validation). I reworked the builder, the messages, the mock and the runner for them; see entries 17 to 19.

## What actually broke or surprised me

1. **Cold start of the pinned n8n.** The first `pnpm dlx` n8n call took about 43 s because of the download and the SQLite build. Later calls took a few seconds. The runner's CLI timeout is 240 s for that reason. After the switch to the global binary this no longer applies.
2. **n8n blocks what the signature check needs.** Before writing any code I built a throwaway workflow to check four things. Raw body: the webhook needs `rawBody: true`, and then the bytes arrive as base64 in the binary `data` property (verified that a body with spaces and a non-ASCII character is byte-identical after decoding). `require('crypto')` in a Code node fails with "Module 'crypto' is disallowed" and `$env` fails with "access to env vars denied" unless `NODE_FUNCTION_ALLOW_BUILTIN=crypto` and `N8N_BLOCK_ENV_ACCESS_IN_NODE=false` are set (I confirmed both failures without the variables). Workflow static data persisted across production executions (counter 1 then 2). The runner sets both variables.
3. **A careless cleanup.** To stop the throwaway server I ran `pkill -f n8n`, which matches every n8n process on the machine. I checked right afterwards and no other n8n was running, and later processes I saw (n8n 2.42.6, started from another tool) were not mine, so I found no evidence of harm, but it was the wrong tool. The runner starts n8n in its own process group and kills exactly that group, also on failure.
4. **Publishing needs a restart.** `n8n publish:workflow` prints "Changes will not take effect if n8n is running". I did not test publishing into a live server; the runner imports and publishes first and starts the server afterwards, and a startup log line confirms both workflows activated.
5. **The webhook is not ready when `/healthz` is.** The n8n log shows `404 The requested webhook "POST ridgeway/lead" is not registered` for requests that arrived after the health check but before activation finished. The runner now probes the production webhook with an unsigned request until it answers 401 (rejected before any side effect), then starts the scenarios.
6. **Mock bug found by reading my own code, before the first run.** The first mock applied a mutation (creating a HubSpot contact) and only then looked at injected faults, so a 503 "failed" create still stored the contact. Fixed by making every state change a function that runs only if no fault is injected; a unit test creates the contact after a 503 and checks it was not stored. Later, for the idempotency work, this became a clean model: faults before the commit change nothing, and an `after_commit` fault commits and then answers late.
7. **`node --test <directory>` does not work on Node 24.** `node --test pest-lead-agent/tests/` failed with `MODULE_NOT_FOUND` because Node tries to load the directory as a module. Fixed with `tests/index.js`, which imports the real test file.
8. **First unit-test run: two real failures.** (a) The guardrail checked `response.error` before `response.type === "error"`, so an Anthropic error body was labelled `llm_request_failed` instead of `llm_error_response`; I swapped the order. (b) My fixtures used `@example.com`, but the spec asks for `.example` domains; I changed every address to `@mail.example` (and fixed the escaped copies in two tests).
9. **My own test typo.** After the switch to 2.42.6 the first full run failed only on `termite_fl_new`: my assertion compared the first 22 characters of the stored message with a string that had a trailing space. Test bug, not a workflow bug.
10. **A mutation check showed an overlap.** To see whether the runner can fail, I temporarily emptied the list of approval pest types. The run failed (on the task description assertion), but the termite lead still came back `approval_required` because its estimated value is $1200, above the $800 threshold. So termite approval has two independent reasons, and the check that bit was the description one. I restored the file; the later runs are on the restored code.
11. **A live run died with a non-assertion error and I lost the message.** The first live run (old bridge) passed. The second one stopped at `hubspot_429` and I had only looked at the last lines of the output, so I never saw the error text. The saved n8n log for that run shows no vendor traffic for the scenario, which fits a slow or hung `claude -p` call outlasting the request timeout, but I did not confirm it. What I changed: the runner now records an error message on the outcome when a request fails before any assertion, the client timeout is long enough for retries, and the replacement bridge has its own queue, per-call timeout and call budget. The later live run, on the new bridge, passed.
12. **The same classification varies between calls.** The deliberately vague message ("something scratching in the attic?") got `other` at 0.4, `other` at 0.35, `rodents` at 0.45 and `other` at 0.4 across four real calls. Every call stayed under the 0.6 threshold, so `needs_review` held and the scenario expectation did not need to change, but it means a pest label on a low-confidence lead should not be trusted or displayed as a fact. A second surprise: a termite lead with visible mud tubes came back urgency `normal`, not `high`, so the termite approval gate rests on pest type and value, not on urgency. I had guessed otherwise in my placeholder recordings.
13. **What the CLI bridge changes about "real responses".** `claude -p --json-schema` reports an internal `stop_reason` of `tool_use` and token usage of about 1.9k input tokens for a small prompt (the CLI's own overhead). The bridge maps the result to a Messages-shaped reply with `stop_reason: end_turn`. The recordings are real model output but not raw API responses, which the README says plainly.
14. **Retry waits slow the suite and expose timing assumptions.** With 3 tries 5 seconds apart, `hubspot_429` takes about 10.8 s, `fieldroutes_down` about 10.7 s and the timeout scenario about 15.6 s; the runner went from roughly 45 s to roughly 70 s. The error-handler wait loop was lengthened to 40 s for the three failing HubSpot attempts.
15. **continueErrorOutput needs both outputs wired.** A node set to `continueErrorOutput` has two outputs; if only the success output is connected, a failure ends the branch silently. The builder connects both to the next step, and a unit test checks it. The failure item carries an `error` field, which the existing `describeHttp` helper handles for the nodes whose next step reads its own input; the `fieldroutes_down` scenario confirmed that against n8n 2.42.6 (3 attempts, then the run continued with no slots). *Corrected 2026-10-11:* an earlier version of this entry read as if every non-critical node was covered. It was not: the Gmail draft node's error item was never read correctly, because the next step looked at `$('Create Gmail draft').first()`, which is output 0 only, so a failed draft was reported as created. No scenario failed Gmail, so nothing noticed. See entry 25.
16. **n8n-mcp reported 15 errors that were false positives.** `validate_workflow` said "Array items must be objects with json property" on 14 Code nodes in one workflow and 1 in the other, without naming a cause. I fed it each module file wrapped in a minimal Code node: only `anthropic.js` and `messages.js` failed, because they contain `return [ 'string', ... ].join('\n')`, which its check reads as the node returning bad items. I rewrote those four functions as `const lines = [...]; return lines.join('\n')`. The produced strings are identical (the unit test that compares recordings with the current request still passes) and the validation now reports 0 errors and 0 warnings.
17. **Mock needed to learn idempotency.** For the `Idempotency-Key` rule the mock stores the first answer per key and replays it, flags writes without a key, and supports a fault that commits a change and then answers after the client's timeout. The scenario `clickup_timeout_after_commit` passes only because the retry reuses the key: the log shows two requests with the same key `13:Create ClickUp CSR task`, the second marked as a replay, and one task in the mock's state.
18. **Personal data in internal messages.** My first messages put the full lead (name, phone, email) into ClickUp and Slack text. After the new rule I moved to ids, links, first name and ZIP, stored the original message on the HubSpot contact, and added a runner check over every Slack, ClickUp and Sheets body for the email, the phone in several formats and the last name. The check has not failed since, so I have no example of it catching a leak; its value is that it would.
19. **Replay-timing risk did not show up.** The duplicate check depends on n8n saving static data when an execution ends, so a second delivery arriving a few milliseconds after the first response could race. In every run (the runner waits for the request log to go quiet before the second delivery) the second request was recognised as a duplicate. This is a limit I could not make fail, not proof of safety under concurrency.

20. **A stray mock server.** My first smoke test of `mock/server.mjs` used `node mock/server.mjs & ... kill %1` in zsh, which did not stop it. I found the process (started 04:48, working directory this demo) in the final cleanup check and killed it. It had been idle on a random localhost port the whole time. The runner itself always closes its own mock.

## 2026-10-11, review fixes: what went wrong or surprised me

21. **n8n static data cannot see a run that is still going.** The fix for "redelivery while a run is in flight" first looked like a small change to the static-data store (answer 409 for a claim that is still `processing`). Before building on it I tested it with a throwaway one-node workflow in a temp n8n folder: a Code node claims `e1` in `$getWorkflowStaticData('global')` and then waits 6 s. A second POST 2 s into the first run answered `{"dup":false}` (it started its own run), the first answered `{"dup":false}`, and a third POST after the first had finished answered `{"dup":true}`. n8n saves static data when an execution ends, so a claim written at the start is invisible to a concurrent request. The first design (static data plus 409) could therefore never produce a 409. I moved the claim to a service n8n calls, the event ledger (a mock here, a database or Redis in production), which also lets the error workflow release a failed run's claim (the error workflow cannot touch the main workflow's static data). The old README line about static data being "enough for sequential redelivery" was true but missed this.
22. **`duplicate_delivery` only passed because n8n remembered an earlier scenario.** The runner resets the mock between scenarios, but not n8n. The scenario sent the `ants_ga_recurring` event again and got `duplicate` only because n8n's static data still held the event from two scenarios earlier. Once the claim moved into the mock's ledger, a reset forgot it and the scenario would have booked the lead a second time. I changed it to seed the ledger with the event as `done` (declared in `scenarios.json`); the real two-deliveries-in-a-row case stays in `replay_two_deliveries`.
23. **The key-reuse assertion could not fail.** The check was "a key that appears twice was marked `idempotent_replay`", but the mock sets that flag precisely when a key appears twice, so it was true by construction. A unit test now feeds logs with a changed body, an unexplained reuse and a surprise redelivery to both the old check (it passes all of them) and the new one (it throws). The new check uses the request bytes (`raw_sha256`), the run id and the injected fault from the log, not the mock's flag. A separate temporary mutation (a copy where the mock stops honoring ClickUp keys) passed the call counts and the key checks and failed only on the new state counts (2 tasks instead of 1), which is what the state assertions are for.
24. **`ps eww` shows nothing for the n8n process on this macOS.** My first environment-allowlist check read n8n's environment with `ps eww -p <pid>` and found no variables at all, so the check failed on its sanity assertion instead of on the canary. I replaced it with a throwaway probe workflow (imported only into the temp n8n, not part of the demo) whose Code node reports which of a list of variable names it can read via `$env`. I ask it about every variable in the runner's own environment plus a canary. The probe showed `PWD`, `SHLVL` and `__CF_USER_TEXT_ENCODING` as visible; those are set by the `sh` shim that launches n8n and by macOS on exec, not inherited, so the test lists them as launcher-added. The probe also confirms the exposure: with the allowlist it sees only the allowlisted names; `N8N_BLOCK_ENV_ACCESS_IN_NODE=false` is why that matters.
25. **A failed Gmail draft was reported as created.** Running the real "Prepare ClickUp CSR task" Code node from the old workflow JSON with fake n8n globals (the helper `tests/code-node.mjs`) showed it: with Gmail's error item as input the node produced no warning, `omitted_reason: null`, and the line "Email draft: created in Gmail, not sent". The fix reads the node's own input item, which is Gmail's answer on the success output and its error item on the error output, instead of `$('Create Gmail draft').first()`. The new scenario `gmail_down` (503 on every try) passed on its first run against n8n 2.42.6, which confirms the shape of the error item. A temporary copy with the old glue restored fails `gmail_down` with `warnings: expected ["gmail_draft_failed"], got []`.
26. **Small mistakes of my own, caught by the tests.** The runner's `tally` helper was defined after its first use (a `ReferenceError` at the end of the first run, after all scenarios had already run); my first redaction test expected `contact_[email removed]` but the email pattern, correctly, swallows the whole `contact_jo@...` token; the regex in my PII deep check did not match the real message text ("(904) 555-0188 or email jo.rivera@..."), which failed the first full run at the last assertion of `pii_in_model_output`; the first execution-history check opened `database.sqlite` in the wrong folder (n8n keeps it in `.n8n/` under `N8N_USER_FOLDER`: "unable to open database file"); the stub `n8n` in the `start.sh` unit test reported `PWD`, `SHLVL` and `_` from its own shell; and my TTL test pruned the ledger entry it then tried to read. None of these was a workflow bug.
27. **Two overclaims in my own documents.** VALIDATION.md said "16 of 16 pass" for the live run while one of the 16 was skipped; the runner counted a skip as a pass. It now prints "N passed, M skipped", and the live row says "15 passed, 1 skipped" (and that the live run predates this fix pass). README and VALIDATION also said the PII check covered "phone (all formats)" when it covered three; both now list the formats, and the check is a hand-written list per fixture rather than a function of the code under test.

28. **`saveDataSuccessExecution: none` did not do what I thought, and my first check could not tell.** The first version of the execution-history check asserted that no execution of the main workflow had `status = 'success'` in n8n's SQLite file. It passed, and I distrusted it because it passed on the first try with 28 rows for the main workflow. Dumping the rows showed 28 executions with `status = 'running'`, `finished = 0` and a `deletedAt` timestamp, each still holding about 2.5 KB of `execution_data`, and for most of them the lead's email address (the initial webhook payload). So with `none`, n8n 2.42.6 writes the first row of every execution, soft-deletes it when the run succeeds, and keeps the payload until its pruner hard-deletes the row (`EXECUTIONS_DATA_HARD_DELETE_BUFFER`, default 1 hour, checked every `EXECUTIONS_DATA_PRUNE_HARD_DELETE_INTERVAL` minutes, default 15). My assertion had been vacuous because those rows never reach `success`. What I changed: the check now requires that every visible (not soft-deleted) row of the main workflow is a failed run with its data, that at least one soft-deleted row was hard-deleted by the pruner during the run (the runner sets a 0-hour buffer and 1-minute passes so that is observable), and it reports how many soft-deleted leftovers remain when n8n stops. `env.sh` sets the buffer to 0 hours. README says what remains true: lead data lives in the database until the next pruner pass (up to the pass interval), invisible in the UI and API, and for failed runs until `EXECUTIONS_DATA_MAX_AGE`.

## 2026-10-11, live HubSpot, phase 1 (offline): what went wrong or surprised me

41. **HubSpot's public docs do not give the two conflict answers I was asked to parse.** The brief said to check the documented status and body of a deal create that conflicts on a unique property, and of a contact create with an existing email ("parse the existing id"). I read the pipelines, properties, search, contacts, deals, associations, error-handling and usage-guidelines pages (logged out, `.md` versions of developers.hubspot.com) and found neither: only the general error format. So the workflow does not parse either body. A refused deal create reads the deal by `ridgeway_event_id`, and a refused contact create reads the contact by `?idProperty=email` (documented). Both work whatever the body says. The mock answers 409 with the body commonly seen from HubSpot ("Contact already exists. Existing ID: ..."), and both its comments say that body is not from the docs. This replaces "parse the id", on purpose.
42. **n8n would retry every 404 three times.** The brief's design reads the deal with `GET ...?idProperty=ridgeway_event_id`, and 404 means "create it". n8n's `retryOnFail` retries any failed request, and a 404 is one, so every new lead would wait 15 s before its deal is created. I found this by reading the HTTP Request node's source in the installed n8n-nodes-base 2.42.4 (the `neverError` and `fullResponse` options), not by running it the slow way. The three reads by unique value now use those two options, so the next Code node gets `{statusCode, body}`. The cost is that a 429 or 5xx on those three reads is not retried by n8n (network errors and timeouts still are). It fails the run into the error workflow instead. The opposite case stays: n8n retries a 409 like any error, so each conflict costs 15 s before the lookup runs (`existing_email_contact_create` takes 16 s, `deal_create_conflict_after_timeout` 26 s).
43. **The search docs say not to send the country code with a phone number.** HubSpot matches phones on area code and local number. The workflow searched `phone EQ +19045550150`. It now also searches the 10 digits as a third filter group. I did not make the mock's phone match normalized, which would be closer to HubSpot: two seeded contacts (40114, 40115) are one person whose stored phones differ only in format, so a normalized match would change which contact some leads update, and the replay is meant to stay the same. No scenario or day lead has a phone that only the new group matches, so the mock's answers did not change (checked against the fixtures).
44. **A re-run of the day would have undone a manager's decision.** While writing the parity check (approve, then re-run against the same portal), I saw that a reused deal still went through "Move deal to Needs approval": an Approved deal would go back to Needs approval. A reused deal now keeps its stage unless it is still in New lead (`needsApprovalMove`). One side effect: in `redelivery_after_failure` the second run no longer re-sends the stage PATCH by key (one PATCH in all, which the check now asserts). Earlier VALIDATION text said it was replayed.
45. **The key-reuse check had to accept a vendor error as a retry's cause.** The rule was "a key reused inside one run needs an injected fault on its first use". A real 409 from the mock (an existing email) is not injected, but n8n retries it with the same key, so the new scenario failed the rule by construction. The rule now also accepts a first use answered with a status of 400 or more. That is slightly weaker: a retry after any vendor error now passes the check. Byte-identical bodies are still required, and the unit test for the old "unexplained reuse" (a 200 first use) still throws.
46. **The plan changed mid-task.** The first reading of the account-info docs listed the `oauth` scope, and I had planned the record-link host from account-info's `uiDomain`. The coordinator then reported, from read-only calls with the real key: it is a service key (not a legacy private app), shaped `pat-na2-` plus a UUID (44 characters); exactly eight scopes, and account-info answers 200 with them; and the portal's app host is `app-na2.hubspot.com`. So the setup script needs no `oauth` scope, the shape check is `pat-<region>-<uuid>`, and the link host comes from `dataHostingLocation` (`na1`: `app.hubspot.com`, otherwise `app-<location>.hubspot.com`). The mock is the only exception: it keeps its `.example` host. I have not seen a real account-info body myself.
47. **The mock's association answer was not HubSpot's.** It returned `{fromObjectTypeId, ...}`, but the v4 default-association reference documents a `BatchResponsePublicDefaultAssociation` (`status`, `results[{from, to, associationSpec}]`). The workflow never read it, so nothing broke. The mock now answers the documented shape.
48. **Everything passed on the first full run, and I distrusted it.** The unit tests had failed on exactly what I had changed on purpose (18 tests, then 4, then 1 wrong count of my own: 39 HTTP nodes instead of 38). Then `verify.mjs` passed 36 of 36 on its first run. I read the request logs of the two new scenarios and of the parity check: the 201 lost after its commit, the three 409s, the `get_deal` 404 then 200, and the four contact 409s are all there. Then I ran one mutation in a scratch copy: the deal body naming the literal `ridgeway_new_lead` stage again. `live_hubspot_parity` failed ("Error in workflow": the fresh portal refused the stage and the lookup found no deal), which is the failure it exists to catch.
49. **Mock behaviour I assumed, not read.** The mock refuses a `dealstage` that is not in the deal's pipeline, and a property that does not exist. The error format is documented (its example is a `PROPERTY_DOESNT_EXIST` error), but that HubSpot refuses an unknown stage is my expectation, not something I found in the docs. The same goes for the 404 body (`OBJECT_NOT_FOUND`) and for the assumption that a read by `ridgeway_event_id` right after a create already sees the deal. Phase 2 will show all three.
50. **HubSpot rejected every `.example` email (2026-10-11, phase 2).** The first live smoke (`evt-d1013-001`, `-010`, `-034`, no fallback) failed 3 of 3 with HTTP 500, after about 19 s each. HubSpot answered `400 INVALID_EMAIL` ("Email address ... is invalid") for the `.example` addresses; the error workflow logged it at "Prepare contact update after conflict", with the email redacted. Nothing was created in HubSpot. The example.com fallback (`<local>+<domain>@example.com`, RFC 2606 reserved) fixed it, and it is now the default in live-HubSpot mode; `--no-hubspot-email-fallback` turns it off and `--hubspot-email-fallback` is accepted and does nothing. The mock still keeps `.example`.
51. **A permanent 4xx costs about 15 s (2026-10-11, phase 2).** The 19 s in entry 50 was n8n retrying the 400 validation error 3 times, 5 s apart: `retryOnFail` retries every error, not only 429 and 5xx. Not fixed; it is a known cost, and any permanent 4xx on a node with retries will take about 15 s before it fails.
52. **What phase 2 confirmed and what it did not (2026-10-11).** Confirmed: `.example` is rejected (entry 50); reads by `idProperty=ridgeway_event_id` found every deal on reruns, including deals created a few minutes earlier (so the assumption in entry 49 about reading right after a create held in practice); HubSpot generated the stage ids. Not exercised live: the create-conflict path (0 conflicts in every run), an unknown `dealstage` (still the mock's behaviour only), the rate-limit tier (no 429 seen at 1.5 s pacing), and what happens when the trial lapses.
